# Проверка соответствия реализации Сервиса СЭД Техническому заданию

Этот скилл задаёт обязательный протокол самопроверки для модели при создании, изменении и ревью любого компонента Сервиса СЭД.

## Источники истины и приоритет

1. **Канон:** локальный файл `ТЗ_Сервис_Документооборота.md` (ред. 3.1, если присутствует в рабочей директории) и нормализованные справочники в папке `references/` этого скилла.
2. **Конфликты с ранними черновиками:** при любом расхождении между ТЗ ред. 3.1 и ранними материалами приоритет имеет **ТЗ ред. 3.1**:
   - поддерживаются **3 клиентских режима** (Толстый в оболочке Оркестратора, Веб, адаптивный Тонкий веб-режим), а не «только веб»;
   - в движке **7 примитивов шагов** (включая `review` для шага «Рассмотрение» с возвратом на `resolution`);
   - в машине состояний **9 статусов карточки**, а `Приостановлено` — это **режим экземпляра маршрута**, не статус карточки;
   - интеграция с 1С идёт через **транзакционный `outbox_events`** и фонового воркера (отказ 1С не блокирует чтение, черновики и выдачу номера).

## Обязательный порядок проверки при работе над задачей

```text
Compliance Checklist:
- [ ] Шаг 1: Определить затронутые подсистемы (M01-M09, worker, web, thick-adapter, temp-auth)
- [ ] Шаг 2: Сверить границы, контракты и запреты по references/architecture-and-boundaries.md
- [ ] Шаг 3: Сверить статусы, 7 примитивов и флаги по references/state-machine-and-engine.md
- [ ] Шаг 4: Сверить SLA, курсорную пагинацию, ERD и права по references/sla-erd-and-doctypes.md
- [ ] Шаг 5: Проверить анти-ловушки и сценарии AC-01..AC-12 по references/anti-traps-and-acceptance.md
- [ ] Шаг 6: Запустить статический аудит и тесты не внутренних контуров
```

### Шаг 6 — обязательные команды верификации

Перед завершением любого этапа или PR модель **обязана** выполнить:

```bash
go run ./.cursor/skills/sed-tz-compliance/scripts/verify_compliance.go
go run ./scripts/secret_guard.go --all
```

Если изменения затрагивают `temp-auth` (в dev-контуре) или внешние контуры СЭД, также запустить соответствующие тесты:

```bash
cd temp-auth && go test -v -race ./...
```

## Жёсткие инварианты («Красные линии» ТЗ)

Нарушение любого из следующих правил считается критическим несоответствием ТЗ:

1. **Изоляция `temp-auth`:** временный сервис аутентификации находится в отдельной корневой папке `temp-auth/` и подключается только через `docker-compose.dev-auth.yml` и переменную `AUTH_BASE_URL`. В основном `docker-compose.yml` и в импортах Go-кода СЭД ссылок на `temp-auth` быть не должно.
2. **Zero-password в СЭД:** СЭД не хранит пароли пользователей, хэши паролей и пароли внешнего учёта 1С; таблица пользователей ограничивается строковым `orchestrator_user_id`.
3. **Нет локальной таблицы уведомлений:** уведомления отправляются только в `POST /api/v1/notifications` с обязательным `source_document_id`.
4. **Append-only аудит:** для таблицы аудита (`audit_log` / `journal`) запрещены `UPDATE` и `DELETE` на уровне приложения и БД; логируются даже просмотры карточки и скачивания файлов.
5. **Идемпотентность и версии:** создание карточки и регистрация номера требуют `Idempotency-Key`; добавление/замена файла после старта маршрута всегда выпускает версию `N+1`.
6. **Курсорная пагинация и серверная фильтрация:** списки `/v1` используют `limit` (<= 100) + непрозрачный `cursor`, а не `OFFSET`; фильтрация по правам и локальным тегам подразделения выполняется на сервере до нарезки страницы.
7. **Автономность при отказе 1С:** запись в `outbox_events` выполняется в одной транзакции с присвоением регистрационного номера; сбой 1С не роняет API.
